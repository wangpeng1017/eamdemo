# LIMS 检测数据录入与报告生成 —— 现状分析与问题全景文档

**项目**：LIMS-Next | **分析日期**：2026-02-23 | **分析范围**：检测项目模板 → 数据录入 → 报告生成 完整链路

---

## 一、系统整体流程图

```
【基础数据配置】
  检测项目管理 → 配置模板（TemplateSchema JSON 存库）
        |
        | （模板在任务数据录入时 ← 目前实际上完全未被读取）
        ↓
【检测任务】
  任务分配 → 数据录入（Fortune-sheet 空白表格）→ 提交
        |
        | sheetData (JSON) 存入 TestTask.sheetData
        ↓
【报告生成】
  /api/report/generate → 按固定列位置提取数据 → 创建 TestReport 记录
        |
        ↓
【导出文档】
  docx-renderer → docxtemplater 填充 Word 模板 → 下载
```

## 二、检测项目模板模块现状

### 2.1 数据结构

模板存储在 `TestTemplate` 表，核心字段是 `schema`（JSON 字符串），结构如下：

```typescript
interface TemplateSchema {
  title: string                    // 表格标题，如"禁限用物质分析记录表"
  header: {
    methodBasis?: string           // 检测依据，如"QC/T 941-2013"
    sampleType?: string            // 样品类型，如"汽车零部件"
  }
  columns: ColumnConfig[]          // 列定义数组
  statistics: StatisticsConfig[]   // 统计行配置（均值/标差/CV）
  environment: boolean             // 是否显示"环境条件：温度 ℃ 湿度 %RH"行
  equipment: boolean               // 是否显示"检测设备："行
  personnel: boolean               // 是否显示"检测人员："行
  defaultRows: number              // 默认空行数
}
```

"禁限用物质分析"模板当前配置：
- `environment: true`、`equipment: true`、`personnel: true`
- 6列：序号、样品编号、检测项目、XRF筛选结果、化学验证结果、限值要求

### 2.2 两套编辑器并存（核心混乱点）

| | 入口 | 组件 | 能配置什么 | 保存格式 |
|---|---|---|---|---|
| **旧编辑器** | 列表页"编辑"按钮 → 弹窗 | `TemplateEditor.tsx` | 列名、列类型、宽度、统计行、环境/设备/人员开关 | 结构化 `TemplateSchema` JSON |
| **新编辑器** | 列表页"编辑内容"按钮 → 新页面 | `EditableTable.tsx` | 仅能输入单元格文字，无结构配置 | 二维数组 → `convertToSchema()` 转换后存库 |

两套编辑器**操作同一个 `schema` 字段**，但数据格式互不兼容：
- 旧编辑器保存完整的 `TemplateSchema`（含列类型、宽度等元信息）
- 新编辑器（EditableTable）保存后，列定义中只剩 `title` 字符串，`dataType`、`width`、`required` 等属性全部丢失

### 2.3 新编辑器的具体问题

**问题A：表头显示"列1 列2 列3"，没有业务含义**

`EditableTable.tsx` 第32行写死：
```typescript
title: `列 ${colIndex + 1}`,  // 永远是"列1 列2 列3..."
```
用户无法从表头看出第几列对应什么字段。

**问题B：表头信息与数据行混在一起**

"禁限用物质分析记录表"、"检测依据：QC/T 941-2013"这些头部信息，经过 `convertSchemaToPreviewData → extractSheetData` 两次转换后变成了普通单元格文字，和数据行没有视觉区分，用户容易误编辑。

**问题C：保存时靠背景色识别列头，容易失效**

`template-converter.ts` 第316行：
```typescript
const headerCells = celldata.filter(c => c.r === headerRowIndex && c.v?.bg?.rgb === "E7E6E6")
```
识别列头的依据是单元格背景色 `E7E6E6`。一旦用户修改了某个单元格，背景色信息丢失，反向解析时列定义就无法正确还原。

## 三、数据录入模块现状

### 3.1 实际情况：模板配置完全未被使用

`task/data/[id]/page.tsx` 的数据加载逻辑：

```
优先级1：如果 task.sheetData 有值 → 直接加载已保存的数据
优先级2：如果 task.testData 有值 → 加载旧格式数据
优先级3：以上都没有 → 加载 getDefaultData()（空白默认表格）
```

**`getDefaultData()` 返回的是 Fortune-sheet 的通用空白表格，与检测项目模板配置的列结构完全无关。**

也就是说：
- 在"检测项目管理"里配置的"序号、样品编号、检测项目、XRF筛选结果、化学验证结果、限值要求"这6列
- 检测工程师打开"数据录入"时，**看到的是一个普通的空白表格**，没有任何预设列头
- 模板配置的列定义、环境条件行、设备信息行，全都没有出现在数据录入界面

### 3.2 数据保存格式

保存时将整个 Fortune-sheet 的 JSON（`sheetData`）原样存入 `TestTask.sheetData`，格式可能是：
- `celldata` 格式（初始加载时）
- `data` 格式（编辑后保存时）

两种格式在加载时有转换逻辑，但转换本身也依赖格式识别的稳定性。

## 四、报告生成模块现状

### 4.1 数据提取逻辑（固定列位置假设）

`/api/report/generate` 的 `extractTestDataFromSheet()` 按如下假设提取数据：

```
col[0] = 检测项目（parameter）
col[1] = 技术要求（standard）
col[2] = 实测值（value）
col[3] = 单项判定（result）
col[4] = 备注（remark）
```

**这个假设与模板配置的列（序号/样品编号/检测项目/XRF结果/化学结果/限值要求）完全不一致。**

### 4.2 原始记录 docx 提取逻辑

`docx-renderer.ts` 的 `extractOriginalRecordResults()` 从 sheetData 提取时假设：

```
col[0] = 检测项目（testItem）
col[1] = 测试1（test1，第一次XRF读数）
col[2] = 测试2（test2，第二次XRF读数）
col[3] = 平均值（avgResult）
col[4] = 备注（remark）
```

又是另一套不同的列假设。

### 4.3 客户报告 docx 中的数据缺口

```typescript
chemResult: r.chemResult || '——',  // 化学验证结果永远是"——"，无来源
temperature: '',  // 检测温度永远为空
humidity: '',     // 检测湿度永远为空
reviewer: '',     // 复核人永远为空
```

### 4.4 一任务只能生成一份报告

`/api/report/generate` 强制检查已有报告，存在则拒绝：
```typescript
if (existingReport) {
  return error('该任务已生成报告，不能重复生成')
}
```
但 QCT 流程需要同时生成：**原始记录**（内部存档）和**客户报告**（对外发送）两份文件。

## 七、根本原因

整个链路存在**三个断层**：

```
断层1：模板配置 ↔ 数据录入
  模板里定义了列，但数据录入界面从不读取模板，直接给空白表格

断层2：数据录入格式 ↔ 报告生成解析
  录入时用Fortune-sheet自由格式，报告生成时按"第几列是什么"硬编码提取，
  二者没有任何约定

断层3：系统数据 ↔ Word模板占位符
  docx模板里的占位符（{temperature}、{chemResult}等）
  对应的数据在系统中没有录入入口
```

这三个断层导致：**即使每个模块单独看都能运行，端到端走完"录入→生成报告"这条路，产出的报告内容是错的。**

## 八、修复方向建议

### 方向A：最小改动——固定 QCT 列结构，统一三处假设

将以下三处统一为同一套 QCT 列定义：
- 模板默认列结构
- 数据录入默认列头
- 报告生成列提取逻辑

QCT 建议列结构：

| 列 | 字段名 | 说明 |
|----|--------|------|
| col[0] | seq | 序号 |
| col[1] | sampleNo | 样品编号 |
| col[2] | testItem | 检测项目 |
| col[3] | test1 | XRF测试1 |
| col[4] | test2 | XRF测试2 |
| col[5] | avgResult | 平均值 |
| col[6] | chemResult | 化学验证结果 |
| col[7] | standardReq | 标准要求 |
| col[8] | conclusion | 结论 |

额外增加：在数据录入页顶部增加结构化表单收集温度、湿度、复核人。

### 方向B：完整重构——打通模板→录入→报告链路

1. 数据录入时读取任务关联的检测项目模板，按模板列定义初始化 Fortune-sheet 列头
2. 报告生成时通过模板列的 `dataIndex` 字段名提取数据（而非按列位置硬编码）
3. 支持一个任务生成多类型报告（`reportType: 'original_record' | 'client_report'`）
4. 删除新编辑器（`EditableTable`），只保留旧编辑器（`TemplateEditor`），消除两套编辑器的混乱
