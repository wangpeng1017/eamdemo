# LIMS 项目业务逻辑漏洞分析报告

> 分析日期: 2026-02-21
> 分析范围: 咨询 → 报价 → 合同 → 委托 → 样品 → 检测任务 → 报告 全链路

---

## 一、核心业务链路总览

```
咨询(Consultation) → 报价(Quotation) → 合同(Contract) → 委托(Entrustment) → 样品(Sample) + 项目(Project)
                                                                                  ↓
                                                              分配 → 检测任务(TestTask) → 检测报告(TestReport)
                                                                                             ↓
                                                                                      客户报告(ClientReport)
```

---

## 二、上下游状态回写漏洞（严重）

### 🔴 BUG-01: 委托创建不回写报价单/合同状态

**现状**：
- 报价单创建 → ✅ 回写咨询单状态为 `quoted`
- 合同创建 → ✅ 回写报价单的 `contractNo` 字段（但 **不更新报价单状态**）
- **委托创建 → ❌ 不回写报价单状态、不回写合同状态**

**问题**：
1. 从报价单生成委托后，报价单状态仍停留在 `approved`，用户无法知道该报价是否已生成委托
2. 合同也无任何状态标记已进入委托阶段
3. 可能导致同一报价单/合同**重复生成多个委托单**

**应有的流转**：
| 操作 | 上游应更新 |
|------|-----------|
| 报价→合同 | 报价单状态 → `contracted` |
| 报价→委托 | 报价单状态 → `entrusted` |
| 合同→委托 | 合同状态 → `entrusted` |

---

### 🔴 BUG-02: 合同创建不更新报价单状态

**代码位置**: `src/app/api/contract/route.ts` L218-220

**现状**：合同创建后仅回写报价单的 `contractNo` 字段：
```typescript
await prisma.quotation.update({
  where: { id: data.quotationId },
  data: { contractNo },  // 只写了编号，没更新 status
})
```

**问题**：报价单状态不变化，用户无法从报价列表看出哪些报价已签合同。

---

### 🟠 BUG-03: 委托删除不回滚上游状态

**代码位置**: `src/app/api/entrustment/[id]/route.ts` L246-303

**现状**：删除委托单时，只清理下游数据（样品、项目、任务），**不回滚上游**的报价单/合同状态。

**后果**：如果委托创建时已回写了上游状态（假设未来修复了 BUG-01），删除委托后应将上游状态恢复。否则上游单据永远停在 `entrusted` 状态，无法再次生成委托。

---

## 三、唯一性/重复检查漏洞

### 🔴 BUG-04: 合同→委托 缺少重复生成检查

**对比**：
| 环节 | 唯一性检查 |
|------|-----------|
| 咨询→报价 | ✅ 检查咨询单是否已生成报价单 |
| 报价→合同 | ❌ **无检查** |
| 报价→委托 | ❌ **无检查** |
| 合同→委托 | ❌ **无检查** |

**问题**：
- 同一张报价单可以反复生成多张合同（无唯一性约束）
- 同一张报价单/合同可以反复生成多张委托单
- 这在 LIMS 业务中通常是不允许的（一对一关系）

---

### 🟠 BUG-05: 编号生成存在并发竞态风险

**问题1 - 咨询单编号**（`consultation/route.ts` L111-126）：
```typescript
const lastConsultation = await prisma.consultation.findFirst({
  where: { consultationNo: { startsWith: prefix } },
  orderBy: { consultationNo: 'desc' },
})
const seq = lastConsultation
  ? parseInt(lastConsultation.consultationNo.slice(-4)) + 1
  : 1
```
使用 `findFirst + 解析序号` 方式，两个并发请求可能获取相同序号。

**问题2 - 报价单编号**（`quotation/route.ts` L139-142）：
```typescript
const count = await prisma.quotation.count({
  where: { quotationNo: { startsWith: `BJ${today}` } }
})
const quotationNo = `BJ${today}${String(count + 1).padStart(4, '0')}`
```
使用 `count + 1` 方式，同样有并发竞态。但编号字段有 `@unique` 约束，所以会报错不会产生脏数据——但**用户体验差**（创建失败需重试）。

**对比**：委托单使用 `generateNo()` 函数（有专门的计数器表），相对安全。

## 四、删除级联漏洞

### 🟠 BUG-06: 删除委托不清理 SampleProcessing 记录

**代码位置**: `src/app/api/entrustment/[id]/route.ts` DELETE

**现状**：删除委托时会清理样品，但样品关联的 `SampleProcessing`（加工记录）和 `SampleRequisition`（借样记录）**没有被清理**。

**Prisma schema 检查**：`SampleProcessing` 表的 `sampleId` 关系**没有** `onDelete: Cascade`，因此删除样品会导致**外键约束错误**。

```
删除委托 → 删除样品 → ❌ SampleProcessing 仍引用该样品 → 数据库报错
```

---

### 🟠 BUG-07: 删除委托不检查已有财务关联

**现状**：删除委托前只检查检测任务，不检查：
- 是否已生成应收账款（`FinanceReceivable`）
- 是否已生成客户报告（`ClientReport` 的非草稿状态）

**后果**：删除有财务记录的委托单，可能导致应收账款与实际业务脱节。

---

## 五、状态流转逻辑漏洞

### 🟡 BUG-08: 样品状态在编辑委托单时被强制重置

**代码位置**: `src/app/api/entrustment/[id]/route.ts` L190

```typescript
// 创建新样品时
status: 'received',  // 硬编码，不考虑送样时间
```

**对比创建委托时**（L387-415）：根据 `sampleDate` 判断是 `pending` 还是 `received`。

**问题**：编辑委托单新增样品时，无论送样日期是否是未来日期，样品状态都是 `received`，与创建时的逻辑不一致。

---

### 🟡 BUG-09: 任务分配按项目名称匹配样品，可能匹配错误

**代码位置**: `src/app/api/entrustment/[id]/projects/[projectId]/route.ts` L143-150

```typescript
const matchedSample = await prisma.sample.findFirst({
  where: {
    entrustmentId: entrustmentId,
    name: project.name  // 按名称匹配
  }
})
```

**问题**：项目名称和样品名称之间的关联是通过**字符串匹配**实现的。如果一个委托单下有多个同名样品，`findFirst` 可能匹配到错误的样品。

---

### 🟡 BUG-10: 委托单状态自动更新逻辑不完整

**代码位置**: `src/app/api/entrustment/[id]/projects/[projectId]/route.ts` L81-107

```typescript
if (allSet.has('assigned') || allSet.has('subcontracted')) {
  newEntrustmentStatus = 'processing'
}
```

**问题**：只检查 `assigned` 和 `subcontracted`，不处理以下场景：
- 所有项目都 `completed` → 委托单应变为 `completed`
- 部分项目 `completed` 部分 `assigned` → 保持 `processing`
- 所有项目被取消 → 委托单状态没有对应处理

## 六、数据一致性问题

### 🟡 BUG-11: 咨询单的评估计数与实际不同步

**代码位置**: `src/app/api/consultation/route.ts` POST

```typescript
assessmentTotalCount: assessorCount,
assessmentPendingCount: assessorCount,
// ...创建时设置初始值
```

**问题**：如果后续评估人被删除或修改，这些计数字段不会自动更新，导致 "已评估 X/Y" 的显示可能与实际不符。计数字段应通过查询计算而不是存储。

---

### 🟡 BUG-12: 编辑委托单时项目删除不检查任务关联

**代码位置**: `src/app/api/entrustment/[id]/route.ts` L66-75

```typescript
const toDeleteIds = existingIds.filter(...)
// 直接删除项目，不检查是否已分配检测任务
await prisma.entrustmentProject.deleteMany({
  where: { id: { in: toDeleteIds } }
})
```

**对比**：样品删除时 ✅ 会检查关联任务。但项目删除时 ❌ 不检查。

**后果**：如果项目已分配任务并生成了 TestTask，删除项目后任务的 `projectId` 变成悬挂引用（虽然 Prisma schema 中 projectId 是可空的，不会报外键错误，但会造成数据孤儿）。

## 七、问题严重度汇总

| 编号 | 问题 | 严重度 | 影响 |
|------|------|--------|------|
| BUG-01 | 委托创建不回写报价/合同状态 | **高** | 无法跟踪单据流转，可能重复建单 |
| BUG-02 | 合同创建不更新报价单状态 | **高** | 同上 |
| BUG-03 | 委托删除不回滚上游状态 | **中** | 上游单据状态不可恢复 |
| BUG-04 | 合同/委托缺少重复生成检查 | **高** | 可能产生重复单据 |

| BUG-06 | 删除委托不清理加工/借样记录 | **高** | 直接导致删除操作数据库报错 |

| BUG-12 | 项目删除不检查任务关联 | **中** | 任务数据孤立 |
